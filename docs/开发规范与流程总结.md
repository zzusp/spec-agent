# 项目开发规范、流程、理念、原则与方法总结

本文档整理并记录本项目中使用的开发规范、流程、理念、原则与方法，便于统一执行与查阅。内容来源：`AGENTS.md`、`rules/delivery.mdc`、`rules/coding.mdc`、`rules/spec-agent.mdc`、`README.md`、`docs/PLUGIN-AND-SKILL-COMPLIANCE.md` 等。

---

## 一、理念（Philosophy）

- **Test-Driven Development（测试先行）** — 先写测试，始终如此；实现阶段以验收项为先，RED → GREEN → REFACTOR。
- **Systematic over ad-hoc（流程优先于猜测）** — 用固定流程与门禁驱动，而非临时判断。
- **Complexity reduction（以简单为首要目标）** — 优先减少复杂度，避免过度设计。
- **YAGNI（You Aren't Gonna Need It / 不要实现你目前不需要的）** — 不为“可能将来会用到”而提前实现功能、抽象或扩展；当前需求需要时再实现；与「最小实现」「避免过度设计」一致。
- **Evidence over claims（先验证再宣布成功）** — 验收默认不通过，只有满足可验证条件才判定通过。

## 二、总体原则

### 2.1 交付与验收

- **唯一完成标准**：用户可用 + 验收通过。
- **禁止**：在全部验收项通过前结束任务；把未解决问题直接抛给用户作为结束方式。
- **行为总纲**：
  - 写完代码不是终点，通过验收才是。
  - 发现问题不是失败，放弃修复才是。
  - 交付的是可用结果，而不是完成过程。

### 2.2 文档与需求（spec-agent）

- **文档顺序强约束**：分析 → PRD → 技术方案 → 验收清单；下游必须基于上游与全局记忆、已确认澄清更新。
- **澄清即真源**：以 `00-clarifications.md` 为准，确认后驱动整份文档重设计，而非局部修补。
- **证据与可追溯**：final-check 做依赖签名与链路校验，保证 R→PRD→TECH→A 可追溯。

### 2.3 代码与实现

- **目标**：代码更少、更稳、更可维护，而不是更多、更快。
- **YAGNI**：不因“以后可能支持多 X”“以后可能换数据源”等假设而提前做抽象、接口层或未用参数；不在当前需求未要求时增加“更通用”的配置或分支。
- **根因修复**：排查与修复从整体功能需求出发，解决根因，禁止硬编码或兜底掩盖问题。

## 三、开发规范（强制）

### 3.1 代码复用（来自 `rules/coding.mdc`）

- 必须优先复用现有代码（已有方法、工具类、公共组件、相似业务逻辑）。
- 禁止为“实现更快/写起来方便”而重复实现已有能力。
- 若最终未复用已有代码，必须给出明确原因。

### 3.2 文件创建约束

- 非必要禁止新建文件。
- 新建仅允许：现有文件职责已明显超载，或新逻辑在语义和职责上无法归入任何现有文件。
- 新建前必须说明：为什么现有文件不适合、新文件职责/边界/预期使用场景；未满足则禁止生成新文件。

### 3.3 注释与可维护性

- 所有新增方法必须包含完整方法注释：方法用途、参数说明、返回值说明。
- 关键业务判断、复杂条件或循环、非直观实现或特殊处理逻辑必须添加行内注释。
- 注释应解释“为什么要这样做”，而非只描述代码行为。

### 3.4 开发阶段额外约束（来自 `rules/delivery.mdc`）

- 遇到不确定性时：允许基于合理假设继续推进，但必须明确标注假设。
- 禁止为推进速度牺牲代码结构或引入明显技术债。

### 3.5 修改前/修改后强制动作

- **修改前**：明确本次修改解决的核心问题、涉及模块/方法、是否存在可复用逻辑、是否影响现有功能。
- **修改后自检**：是否复用了已有代码、是否避免不必要新文件、是否补充注释、是否未引入破坏性副作用、是否符合整体功能需求；未通过自检禁止输出最终代码。

## 四、流程

### 4.1 交付闭环（强制执行、不可跳过）

按以下阶段顺序执行并自动切换：

```
开发实现 → 测试/验收 → 发现问题 → 修复问题 → 测试/验收 → … → 全部通过 → 最终交付
```

- 认为开发完成时，必须明确声明进入“测试/验收阶段”并执行验收规则。
- 验收 → 失败 → 修复 → 再验收为正常流程；禁止部分通过即进入交付阶段。

### 4.2 需求文档工作流（spec-agent）

1. 优先使用 `/spec-agent-chat <消息>` 作为统一入口（用户明确要求直出全量文档时使用 `/spec-agent-task <原始需求>`）。
2. 调用端 AI 按固定顺序写文档：`analysis` → `prd` → `tech` → `acceptance`。
3. 下游文档必须基于上游；四份文档须纳入全局记忆与已确认澄清，prd/tech/acceptance 须含依赖签名。
4. 使用脚本做状态与门禁：`sync-memory`、`check-clarifications`、`final-check`；使用阶段子代理时配合 `subagent-init`、`subagent-context`、`subagent-stage`、`subagent-status`。
5. 重复澄清闭环直至检查通过。

### 4.3 澄清应用与文档更新（单一事实来源）

- 应用已确认澄清时：根据澄清的「用户确认/补充」与「解决方案」修订**所有受影响的章节与整体设计**，不得仅增加 C-xxx 引用即视为完成。
- 每份文档更新时须**整体回顾整篇文档**；有矛盾或更优方案且可自行收敛则直接修正，需用户决策则追加到澄清文档（新澄清项、状态待确认）。
- 顺序：先按澄清修订相关段落，再通读整份文档做一致性检查；新冲突、遗漏或需用户确认的点补充到澄清或当轮修正。
- 每次更新任一份文档（01～04、00-clarifications）时，在该文档的「修订记录」表中追加一行（日期 yyyy-MM-dd、修订人、修订内容摘要）。
- 验收项（A-xxx）的验收步骤与通过标准须可执行、可断言，便于 TDD；修改或新增验收项时保持可测试性。
- 纯文档质量/表述问题可直接在文档中修正，不扩充澄清列表；需用户决策的内容才追加为待确认澄清项。

### 4.4 项目无法启动时的处理

1. 定位启动失败原因（编译、依赖、配置、环境等）。
2. 主动尝试修复并重新启动。
3. 若仍无法修复：至少尝试三种不同方案，记录每种尝试与失败原因，标记相关验收项为不通过，给出完整失败说明，不中断流程。

### 4.5 回归测试

- 按顺序执行（禁止并行）：
  ```bash
  python scripts/regression_smoke.py
  python scripts/regression_edge_cases.py
  python scripts/regression_split_skill_contract.py
  ```
- `regression_edge_cases.py` 会临时覆盖配置做负向测试；Windows 上两个锁/并发测试会跳过，锁语义在 Unix 上验证。

## 五、方法

### 5.1 测试驱动开发（TDD）与 RED-GREEN-REFACTOR

当需求来自 spec-agent 产出（尤其存在 `spec/**/04-acceptance.md`）时，实现阶段应采用 TDD：

- **RED**：根据 04-acceptance 中的验收项（A-xxx）与验收步骤/通过标准先写**失败**的测试，运行确认失败。
- **GREEN**：只写能让当前测试通过的**最小实现**，不提前做多余设计。
- **REFACTOR**：在测试保持通过的前提下整理结构、命名与重复，不改变行为。

单次循环建议以一条验收项（或一个可独立验证的小行为）为一轮；禁止未红就写实现、未绿就重构。

### 5.2 验收最低通过标准（须全部满足）

每个验收项须同时满足：

1. 项目能成功启动（如适用）。
2. 接口或功能调用成功（无 4xx、5xx 或超时）。
3. 核心业务逻辑被真实执行。
4. 执行结果可验证（返回值、数据变化或状态变化）。
5. 有明确日志或等价执行证据。

任一不满足则该验收项不通过。禁止表面测试、接口失败仍判通过、无日志无证据判通过。

### 5.3 问题与修复

- 触发修复：验收不通过、日志缺失或不完整、无法确认核心路径是否执行、项目无法启动。
- 要求：明确根因而非表面修补；修复方案考虑对整体功能的影响；修复后必须重新进入测试/验收，禁止“修完即结束”。

### 5.4 最终交付输出

仅在**所有验收项全部通过**后允许进入最终交付阶段。交付时须明确给出：

- 已实现的功能点
- 验收方式及通过依据
- 已解决的问题列表
- 非关键已知限制（若有）的说明

## 六、命令契约与多需求约定

- **命令契约**：以 `AGENTS.md` 的 Command contract 为单一事实来源；子命令、入参、输出、副作用见该表。
- **多需求**：优先对变更类命令使用显式 `--name` 或 `--path`；未指定时由 `spec/.active` 解析；必要时先 `set-active` 再操作。
- **Dry-run**：变更类命令支持 `--dry-run` 预览；可选在 `scripts/spec-agent.config.json` 中设置 `dry_run_default: true`。

---

## 七、插件与技能约定（摘要）

- **仓库结构**：符合 Cursor Plugin 布局；skills 在 `skills/`，agents 在 `agents/`，rules 在 `rules/`；统一入口为 `spec-agent-chat`，`spec-agent-task` 作为显式全量生成入口。
- **Skill 触发**：用户通过斜杠命令 `/spec-agent-<name>` 触发；编排在 spec-agent-task 内由 AI 按文档与脚本完成，不依赖多 skill 程序化链式调用。
- **脚本**：唯一入口为 `scripts/spec_agent.py`，从用户项目根目录（CWD）执行；子命令与参数以 `AGENTS.md` 为准；运行时配置为 `scripts/spec-agent.config.json`，与 plugin.json 分离。
- **澄清**：仅配置中规定的状态有效；已确认状态由配置键 `clarify_confirmed_status` 定义。
- **DB 上下文**：需求或澄清中含 DB 连接信息时，分析阶段须做 schema 探查；通过 AGENTS 中约定的「方式 B」临时脚本契约与 `inspect-db` 命令，将**全量 schema** 写入公共文档 `spec/db/{scheme}-{dbname}-schema.md`，各需求 `01-analysis.md` 的「数据库现状」仅保留对公共文档的引用行。
